0. Карта процесса: что именно делает сборщик

Скрейпинг (web scraping) — это автоматизированное получение данных с веб-ресурсов. Типичная программа состоит из отдельных этапов. Не смешивайте их в одну длинную функцию: тогда непонятно, где возникла ошибка.

  1. Постановка задачи. Определите конкретный набор полей: например, IPA-символ, название звука, пример слова, URL аудио.
  2. Разведка. Посмотрите страницу в браузере: HTML, DOM, запросы Network, источники медиа, правила сайта.
  3. Получение. Скачайте HTML или JSON через HTTP-клиент; при необходимости используйте настоящий браузер.
  4. Разбор. Извлеките нужные поля через CSS-селекторы, XPath, JSON-пути или анализ атрибутов.
  5. Нормализация. Приведите ссылки к абсолютным URL, удалите дубликаты, проверьте типы и пропуски.
  6. Загрузка ресурсов. Сохраните аудио и изображения, не перепутав HTML-страницу ошибки с бинарным файлом.
  7. Экспорт и проверка. Запишите JSON/CSV/TSV/БД, составьте отчёт и проверьте результат вручную.
Главный принцип: сначала выясните, откуда браузер получает нужные данные. Самый надёжный путь часто не «распарсить весь сайт», а найти JSON API или прямую публичную ссылку на ресурс и аккуратно использовать её.

Сборщик не угадывает содержимое страницы. Он получает конкретный HTTP-ответ или состояние браузера и затем извлекает из него данные.

1. Разведка сайта до написания кода

Самая важная привычка — не начинать сразу с Python. Сначала откройте страницу в браузере и выясните, где реально лежат интересующие данные.

1.1. View Source и Elements — не одно и то же

  • View page source / Просмотр кода страницы показывает исходный HTML, который сервер прислал первоначально.
  • Elements / Элементы показывает текущий DOM после выполнения JavaScript, кликов, подгрузки данных и изменений страницы.
  • Если в Elements звук присутствует, а в исходном HTML его нет, значит данные могли быть добавлены JavaScript-кодом.

1.2. Инструменты разработчика

  1. Откройте страницу и нажмите F12 или Ctrl+Shift+I.
  2. Перейдите во вкладку Network и включите Preserve log, чтобы не терять запросы при переходах и редиректах.
  3. Очистите журнал, перезагрузите страницу.
  4. Отфильтруйте запросы по Media, Fetch/XHR, затем при необходимости по Img.
  5. Нажмите кнопку звука на странице и посмотрите, какой новый запрос появился. Откройте его: изучите Request URL, Status, Headers, Response и Initiator.
  6. Нажмите правой кнопкой по запросу → Copy → Copy URL или Copy as cURL. Не публикуйте скопированные запросы, если там присутствуют cookies или токены.
Важно: запрос с типом media не обязательно содержит весь файл. Сайт может использовать поток, несколько фрагментов, blob URL или внутренний API. Смотрите на Content-Type, Response и Initiator.

import requests
from bs4 import BeautifulSoup

url = "https://example.com/page"
headers = {
    "User-Agent": "StudyCollector/1.0 (contact: your-email@example.org)"
}

response = requests.get(url, headers=headers, timeout=(8, 20))
response.raise_for_status()  # остановиться на HTTP 4xx/5xx

print("Код ответа:", response.status_code)

requests получает ответ сервера. BeautifulSoup ничего не загружает из интернета: он только разбирает уже полученный HTML/XML. Такое разделение полезно для отладки.

2.3. Почему используется response.content

response.content возвращает байты, а BeautifulSoup пытается определить кодировку по самому документу. response.text уже является строкой, декодированной Requests. Оба подхода работают часто, но при проблемах с кодировкой важно сравнить объявленную кодировку, заголовки ответа и результат декодирования.

Из HTML можно получить адрес вроде /media/phonemes/th.mp3. Это не полный URL. Преобразуйте его через urllib.parse.urljoin, используя адрес страницы, на которой нашли ссылку.

3.3. Атрибуты, а не только теги

Источник аудио может храниться не в src, а в data-src, data-audio, data-file, onclick или внутри JSON в script. Исследуйте DOM: универсального имени атрибута не существует.

for element in soup.select("[data-audio], [data-src], audio, source"):
    print(element.name, element.attrs)

# Inline JavaScript тоже иногда содержит адрес ресурса:
for script in soup.find_all("script"):
    script_text = script.string or script.get_text()
    if ".mp3" in script_text or ".ogg" in script_text:
        print(script_text[:1000])
Не полагайтесь на один CSS-селектор. Дизайн сайта может измениться. Лучше выделить отдельную функцию parse_card() и проверять, что извлечённые значения имеют ожидаемый формат.

4. Аудио, изображения и другие файлы

Загрузить HTML и сохранить MP3 — две разные операции. Медиафайл является бинарным содержимым HTTP-ответа; не записывайте его через response.text.

4.1. Найти известные типы источников

from bs4 import BeautifulSoup
from urllib.parse import urljoin

soup = BeautifulSoup(html, "html.parser")

media_urls = []
for tag in soup.select("audio[src], audio source[src], video[src], img[src]"):
    media_urls.append(urljoin(page_url, tag["src"]))

# Не забудьте варианты с data-src и srcset.
for tag in soup.select("img[data-src], source[srcset]"):
    if tag.has_attr("data-src"):
        media_urls.append(urljoin(page_url, tag["data-src"]))
    if tag.has_attr("srcset"):
        # srcset содержит несколько кандидатов с указанием ширины/density.
        print("srcset:", tag["srcset"])

4.2. Безопасное сохранение бинарного файла

from pathlib import Path
from urllib.parse import urlparse
import requests

url = "https://example.com/media/phoneme.mp3"
out = Path("downloads/phoneme.mp3")
out.parent.mkdir(parents=True, exist_ok=True)

with requests.get(url, stream=True, timeout=(10, 30)) as response:
    response.raise_for_status()
    content_type = response.headers.get("Content-Type", "")
    if "text/html" in content_type.lower():
        raise ValueError("Сервер вернул HTML, а не аудио")

    total = 0
    with out.open("wb") as file:
        for chunk in response.iter_content(128 * 1024):
            if not chunk:
                continue
            total += len(chunk)
            if total > 30 * 1024 * 1024:
                raise ValueError("Файл превысил допустимый размер")
            file.write(chunk)

print("Сохранено:", out, "байт:", out.stat().st_size)

4.3. Почему расширение файла не гарантирует формат

URL может не иметь расширения, а сервер способен вернуть HTML-страницу с HTTP 200. Проверяйте HTTP-статус, Content-Type и сигнатуру файла. Например, MP3 часто начинается с ID3 или MPEG frame sync; WAV — с RIFF/WAVE; Ogg — с OggS. Для массового импорта полезно вести отчёт: URL, MIME-тип, размер, результат проверки.

4.4. Символы транскрипции

Большинство IPA-символов — это символы Unicode, а не отдельные изображения. Их лучше хранить как текст в UTF-8: например θ, ð, ʃ, ŋ. Отдельный SVG/PNG нужен только если на исходном сайте символ представлен рисунком или специальным спрайтом. В таком случае сначала проверьте Elements: может быть это SVG, CSS-псевдоэлемент либо web-font.

Практика 2. Скачайте один MP3-файл и проверьте его: размер больше нуля, браузер его открывает, начало файла не содержит HTML. Только после этого масштабируйте загрузку на весь список.

Перенаправление — обычный ответ HTTP, который сообщает клиенту, куда отправить следующий запрос. Несколько последовательных редиректов — это цепочка, а не ошибка сама по себе.

5.2. Зачем нужны заголовки

  • User-Agent идентифицирует HTTP-клиент. Указывайте честный, понятный идентификатор; не выдавайте себя за браузер для обхода запретов.
  • Referer сообщает страницу, с которой пришёл запрос. Некоторые сайты проверяют его при отдаче медиафайлов.
  • Accept / Accept-Language описывают желаемые типы ответа и язык.
  • Cookie хранит состояние сессии. Используйте requests.Session(), а не копируйте cookies в публичный код.
  • Authorization может содержать секретный токен. Не публикуйте его и не помещайте в репозиторий.

6.2. Получить страницу после выполнения JavaScript

import asyncio
from playwright.async_api import async_playwright
from bs4 import BeautifulSoup

async def main():
    async with async_playwright() as p:
        browser = await p.chromium.launch(headless=True)
        page = await browser.new_page()

        response = await page.goto(
            "https://example.com/dynamic",
            wait_until="domcontentloaded",
            timeout=45000,
        )
        print("HTTP:", response.status if response else None)
        print("После редиректов:", page.url)

        # Предпочтительнее ждать конкретный элемент, чем спать фиксированное время.
        await page.locator(".sound-card").first.wait_for(timeout=15000)
        html = await page.content()
        soup = BeautifulSoup(html, "html.parser")
        print("Карточек:", len(soup.select(".sound-card")))

        await browser.close()

asyncio.run(main())

7. Найти API, через которое сайт получает данные

Многие страницы получают карточки, списки, профили и аудиоссылки из JSON API. Браузер посылает запрос, сервер возвращает JSON, JavaScript строит интерфейс. Часто это проще парсинга DOM.

7.1. Алгоритм поиска

  1. Откройте Network → Fetch/XHR.
  2. Перезагрузите страницу и найдите запросы с JSON в Response.
  3. Посмотрите URL, метод, Query String Parameters, Request Payload и заголовки.
  4. Повторите действие на странице (поиск, следующая страница, выбор звука) и сравните запросы.
  5. Проверьте, можно ли получить тот же публичный ответ через Requests без обхода авторизации или защиты.

7.3. Почему API лучше HTML

  • Структурированные поля уже отделены друг от друга.
  • Меньше зависимости от дизайна и CSS-классов.
  • Обычно меньше объём ответа.
  • Проще пагинация, сортировка и проверка типов.

Но endpoint может быть внутренним, недокументированным или защищённым. Не считайте обнаружение URL разрешением на массовый сбор. Учитывайте условия сайта и ограничения использования API.

8. Пагинация, бесконечная прокрутка и несколько страниц

Данные редко ограничиваются одной страницей. Сайт может использовать обычные адреса ?page=2, кнопки «Далее», API-параметры offset/limit или cursor pagination.

8.1. Обычная пагинация

from urllib.parse import urljoin
from bs4 import BeautifulSoup
import requests

session = requests.Session()
base = "https://example.com/catalog"
page_url = base
seen = set()

for page_number in range(1, 51):  # жёсткий лимит
    response = session.get(page_url, timeout=20)
    response.raise_for_status()
    soup = BeautifulSoup(response.content, "html.parser")

    for card in soup.select(".item-card"):
        item_id = card.get("data-id")
        if item_id and item_id not in seen:

            print(item_id)

    next_link = soup.select_one("a.next[href]")
    if not next_link:
        break
    next_url = urljoin(response.url, next_link["href"])
    if next_url == page_url:
        break
    page_url = next_url

Сначала изучите Network: часто прокрутка вызывает API, а не загружает данные из HTML. Если без браузера нельзя, прокручивайте небольшими порциями, ждите появления новых элементов и проверяйте, увеличилось ли количество карточек.

Обязательные ограничители: максимальное число страниц, максимальное число элементов, дедупликация, таймаут, пауза между запросами и условие остановки. Бесконечный цикл в сборщике — это не мелкая ошибка: он может перегрузить сайт и ваш компьютер.

9. Как сделать загрузчик устойчивым

Одноразовый скрипт может работать случайно. Надёжная программа должна переживать сетевые ошибки, временные блокировки, частично повреждённые данные и повторный запуск.

9.1. Retry и backoff

from requests import Session
from requests.adapters import HTTPAdapter
from urllib3.util.retry import Retry

retry = Retry(
    total=4,
    connect=4,
    read=2,
    status=3,
    backoff_factor=1.5,
    status_forcelist=[429, 500, 502, 503, 504],
    allowed_methods=["GET", "HEAD"],
    respect_retry_after_header=True,
)

session = Session()
adapter = HTTPAdapter(max_retries=retry)
session.mount("https://", adapter)
session.mount("http://", adapter)

9.2. Дедупликация

Один ресурс может встретиться как абсолютный и относительный URL, с разными fragment-частями или в нескольких карточках. Нормализуйте адреса, но не удаляйте query-параметры без понимания: иногда это токен или идентификатор файла.

9.3. Контроль целостности

  • Не сохраняйте файл, если ответ — HTML или JSON-ошибка.
  • Проверяйте размер и расширение по MIME/сигнатуре.
  • Считайте SHA-256, если важна идентичность файлов и повторная загрузка.
  • Сохраняйте промежуточный manifest: исходный URL, финальный URL, имя файла, тип, размер и связанный IPA-символ.
  • Ошибки отдельных элементов записывайте в журнал, не прекращая всю задачу.

9.4. Лимиты и задержки

import time

MAX_ITEMS = 100

9.5. Кеширование

Сохраняйте уже обработанные URL в JSON/SQLite. При повторном запуске не загружайте повторно то, что успешно скачано и прошло проверку. Для больших проектов используйте SQLite: уникальный ключ по нормализованному URL или ID источника.

11. Доступ, ограничения и безопасное обращение с данными

  • Сначала ищите официальный API, открытые данные или кнопку экспорта.
  • Проверьте Terms of Service, лицензию, robots.txt и правила использования медиа. robots.txt — техническая подсказка о предпочтениях обхода, а не универсальная лицензия на сбор и не замена правовой оценке.
  • Ограничивайте скорость запросов. Не отправляйте десятки параллельных запросов к небольшому сайту без необходимости.
  • Не обходите paywall, CAPTCHA, аутентификацию, антибот-защиту или ограничения API.
  • Не собирайте персональные или чувствительные данные без законного основания и необходимости.
  • Не публикуйте cookies, access tokens, session IDs, личные данные и приватные URL с временными токенами.
  • Не загружайте и не распространяйте чужие аудио/изображения публично без разрешения или подходящей лицензии. Для личного использования всё равно проверяйте условия источника и применимое право.
Уважайте отказ сервера. Если сервер возвращает 403/429, просит войти или прямо блокирует автоматизированный доступ, не пытайтесь маскировать или обходить ограничения. Уменьшите частоту, найдите официальный канал доступа либо остановитесь.

14. Форматы данных за пределами HTML

Сайт может отдавать не HTML, а JSON, XML, CSV, RSS/Atom, JSON-LD, PDF или архив. Сначала определи формат по заголовку Content-Type и содержимому, а уже потом выбирай парсер. Расширение URL не является надёжным признаком формата.

14.1. JSON-LD и встроенные данные

JSON-LD часто находится в script[type="application/ld+json"]. Это структурированные данные, часто описывающие сущности страницы. Иногда SPA встраивает начальное состояние в script-блок с собственным идентификатором. Разбирай содержимое через json.loads, а не регулярным выражением по всему документу.

import json
from bs4 import BeautifulSoup

soup = BeautifulSoup(html, "html.parser")
for node in soup.select('script[type="application/ld+json"]'):
    raw = node.string or node.get_text()
    try:
        data = json.loads(raw)
    except json.JSONDecodeError:
        continue
    print(data.get("@type"), data.get("name"), data.get("url"))

14.2. XML, RSS и Atom

XML чувствителен к пространствам имён (namespaces). Простой поиск по имени тега может не найти элемент, если в документе используются namespace-префиксы. Для небольших файлов подойдёт стандартный xml.etree.ElementTree; для недоверенного XML не включай обработчики внешних сущностей и используй безопасные настройки/библиотеки.

import xml.etree.ElementTree as ET

root = ET.fromstring(xml_text)
for item in root.findall(".//item"):
    title = item.findtext("title")
    link = item.findtext("link")
    print(title, link)

# В RSS/Atom проверяй namespace и структуру конкретного источника.

14.3. CSV, PDF и архивы

Для CSV используй модуль csv, задавая кодировку и корректный разделитель. PDF может содержать текст, сканы, таблицы или смешанный контент: сначала проверь, есть ли текстовый слой. Для извлечения текста применяют специализированные библиотеки, а OCR — только если документ действительно состоит из изображений. Архивы распаковывай с ограничением размера/количества файлов и защитой от path traversal.

Практика. Найди по одному открытом примеру JSON-LD, XML/RSS и CSV. Для каждого определи MIME, распарси минимум три поля и сохрани в единую модель Python.
Важно: не считай PDF или архив безопасным только потому, что сервер вернул 200. Проверяй формат, размер и происхождение файла.

15. REST, GraphQL и исследование контрактов API

Если сайт получает данные через JSON, изучи не только URL, но и весь контракт: HTTP-метод, query-параметры, тело, заголовки, авторизацию, схему ответа, ошибки, лимиты и пагинацию. Обнаруженный через DevTools endpoint может быть внутренним и нестабильным; наличие запроса в браузере не делает его публичным API.

15.1. REST: запросы и валидация структуры

import requests

response = requests.get(
    "https://api.example.org/v1/sounds",
    params={"language": "en", "limit": 50},
    timeout=(5, 20),
)
response.raise_for_status()
payload = response.json()

items = payload.get("items")
if not isinstance(items, list):
    raise ValueError("Expected items to be a list")

for item in items:
    if not isinstance(item.get("id"), str):
        raise ValueError("Invalid item id")

15.2. GraphQL

GraphQL часто использует один endpoint и POST-запрос с полями query, operationName и variables. Поэтому одного URL недостаточно, чтобы понять операцию. В Network изучи Payload и Response. В ответе проверяй не только data, но и массив errors. Для разрешённых публичных API пользуйся официальной схемой и ограничениями.

query = """
query Sounds($language: String!, $first: Int!) {
  sounds(language: $language, first: $first) {
    id
    symbol
    audioUrl
  }
}
"""
response = requests.post(
    API_URL,
    json={"query": query, "variables": {"language": "en", "first": 20}},
    timeout=20,
)
response.raise_for_status()
data = response.json()
if data.get("errors"):
    raise RuntimeError(data["errors"])

15.3. Пагинация по курсору

Cursor — непрозрачный маркер продолжения, а не обязательно номер страницы. Передавай его обратно без самостоятельного изменения. Учитывай флаг hasNextPage, next_cursor или next. Для контроля полноты сохраняй уникальные ID и checkpoint.

cursor = None
seen = set()
while True:
    params = {"limit": 100}
    if cursor is not None:
        params["cursor"] = cursor
    data = session.get(API_URL, params=params, timeout=20).json()
    for item in data["items"]:
        seen.add(item["id"])
    cursor = data.get("next_cursor")
    if not cursor:
        break
Практика. Изучи открытый API. Зафиксируй его контракт в README: метод, endpoint, параметры, схема ответа, пагинация, ограничения, правила доступа и возможные ошибки.

16. Время выполнения JavaScript и правильные ожидания

Динамическая страница не имеет одного универсального момента «готовности». DOMContentLoaded означает, что исходный HTML разобран; load ждёт загрузку основных зависимостей; SPA может продолжать подгружать данные после обоих событий. Сайты с аналитикой, polling или WebSocket могут никогда не достигать сетевого idle.

16.1. Ждать наблюдаемое состояние

await page.goto(url, wait_until="domcontentloaded")

# Ждём конкретную карточку, а не произвольные 5 секунд.

# После действия проверяем ожидаемый результат.

21. WebSocket и Server-Sent Events

WebSocket после HTTP-handshake создаёт двусторонний канал сообщений. SSE (Server-Sent Events) передаёт события от сервера клиенту через HTTP и обычно является однонаправленным потоком. В Network ищи фильтр WS или EventStream.

Перед чтением потока выясни, нужен ли весь live-stream или только начальный снимок данных. Обрабатывай heartbeat, reconnect, повторные события и разрыв соединения. Всегда задавай предел времени или числа сообщений и сохраняй checkpoint, если задача предполагает продолжение.

import aiohttp
import asyncio

async def read_sse(url, max_events=20):
    timeout = aiohttp.ClientTimeout(total=None, sock_read=45)
    async with aiohttp.ClientSession(timeout=timeout) as session:
        async with session.get(url) as response:
            response.raise_for_status()
            count = 0
            async for line in response.content:
                text = line.decode("utf-8", errors="replace").rstrip()
                if text.startswith("data:"):
                    print(text[5:].strip())
                    count += 1
                    if count >= max_events:
                        break
Практика. На демонстрационном ресурсе найди WS или SSE. Опиши handshake, направление обмена, формат сообщений, механизм переподключения и способ завершения клиента.

22. Асинхронные HTTP-клиенты и контроль конкуренции

Асинхронность полезна, когда много сетевых операций и время тратится на ожидание. asyncio координирует корутины; для HTTP можно использовать httpx или aiohttp. Асинхронность не означает отсутствие ограничений: используй Semaphore, таймауты и лимиты на домен.

import asyncio
import httpx

async def fetch(client, sem, url):
    async with sem:
        response = await client.get(url, timeout=20)
        response.raise_for_status()
        return response.text

async def main(urls):
    sem = asyncio.Semaphore(2)  # не больше двух одновременных запросов
    async with httpx.AsyncClient(follow_redirects=True) as client:
        tasks = [fetch(client, sem, url) for url in urls]
        return await asyncio.gather(*tasks, return_exceptions=True)

# asyncio.run(main(urls))

CPU-bound задачи требуют другого подхода, например process pool. Не запускай сотни запросов одновременно. Сравнивай скорость с количеством ошибок и допустимой нагрузкой, а не только по времени завершения.

Практика. Сравни последовательный режим и Semaphore(2) на локальном сервере/учебном API. Измерь время, число ошибок и максимальное число одновременных запросов.

25. Надёжность: retry, Retry-After, checkpoint и возобновление

Разделяй временные и постоянные ошибки. Для 429 учитывай Retry-After и уменьшай интенсивность. Для сетевых ошибок используй ограниченный exponential backoff с jitter. Не повторяй автоматически неидемпотентный POST без продуманной схемы идемпотентности. 401/403 чаще требуют остановки и проверки доступа, а не повторов.

import time, random, requests

def get_with_retry(url, attempts=4):
    for attempt in range(attempts):
        try:
            r = requests.get(url, timeout=(5, 20))
            if r.status_code == 429:
                wait = int(r.headers.get("Retry-After", "5"))
                time.sleep(min(wait, 120))
                continue
            r.raise_for_status()
            return r
        except (requests.Timeout, requests.ConnectionError):
            if attempt == attempts - 1:
                raise
            time.sleep(min(2 ** attempt, 30) + random.uniform(0, .5))
    raise RuntimeError("Retry budget exhausted")

Логируй ID обрабатываемой записи, статус, размер и причину ошибки. Checkpoint может хранить обработанные ID, последний cursor, номер страницы и статус каждой загрузки. При повторном запуске программа должна безопасно пропускать уже проверенные файлы и продолжать незавершённые.

Заголовок Retry-After может содержать число секунд или HTTP-date. Если используешь собственную реализацию retry, обрабатывай оба формата и ограничивай максимальное ожидание. Не делай несколько параллельных повторов после одного 429.

Практика. Создай статусы pending/running/ok/failed в SQLite. Прерви процесс после нескольких записей и запусти повторно. Докажи, что файлы не повреждаются и завершённые задачи не дублируются.

26. Безопасность: SSRF, path traversal, архивы и секреты

Сборщик может стать уязвимым, если скачивает адреса из внешнего HTML или строит путь на диске из пользовательского ввода. SSRF — ситуация, когда программа по недоверенному URL обращается к неожиданному серверу, например localhost или внутреннему IP. Проверяй схему, host, адрес назначения и каждый редирект; в серверных приложениях одной проверки строкового hostname может быть недостаточно из-за DNS rebinding.

26.1. Разрешённые домены и безопасное имя

from urllib.parse import urlsplit
from pathlib import Path

ALLOWED_HOSTS = {"example.org", "cdn.example.org"}

def validate_url(url):
    parts = urlsplit(url)
    if parts.scheme != "https" or parts.hostname not in ALLOWED_HOSTS:
        raise ValueError("URL is outside the allowlist")

def safe_path(root, filename):
    root = Path(root).resolve()
    target = (root / filename).resolve()
    if target != root and root not in target.parents:
        raise ValueError("Path traversal detected")
    return target

26.2. Секреты и вредные файлы

Cookies, bearer tokens, storage state и API keys храни в переменных окружения или секрет-хранилище, не в исходниках. Не логируй Authorization. Ограничивай размеры, типы и глубину распаковки. Для ZIP учитывай zip-slip и архивные бомбы. Не запускай скачанные скрипты и не открывай неизвестные файлы автоматически.

Практика. Проверь URL с localhost, private IP, внешним доменом и редиректом на внешний домен. Проверь имя файла с ../ и абсолютным путём. Все опасные случаи должны быть отклонены.

31. HTTP и сеть глубже: что происходит между Python и сайтом

Requests скрывает значительную часть сетевой механики. Это удобно, но для диагностики нужно понимать уровни: DNS находит адрес узла; TCP или QUIC обеспечивает транспорт; TLS защищает соединение; HTTP передаёт запрос и ответ; приложение сайта интерпретирует маршрут, заголовки, cookies и тело. Ошибку одного уровня нельзя исправить изменением CSS-селектора.

31.1. HTTP-сообщение и согласование представления

Один URL может вернуть разное содержимое в зависимости от Accept, Accept-Language, Accept-Encoding, cookies и других параметров. Это называется content negotiation. При сравнении браузера и Python сравни не только URL, но и метод, заголовки, тело запроса, cookies, статус и конечный URL. Не копируй бездумно все браузерные заголовки: выясни, какие действительно влияют на ответ.

url = "https://example.org/start"
with requests.Session() as session:
    response = session.get(url, timeout=(5, 20), allow_redirects=True)

31.3. Кэш и условные запросы

Сервер может прислать ETag или Last-Modified. При повторном сборе можно отправить If-None-Match или If-Modified-Since. Ответ 304 означает, что можно использовать уже сохранённую копию, если она действительно есть и относится к правильному варианту ресурса. Учитывай Vary: представление может зависеть от языка или других request headers.

headers = {}
if saved_etag:
    headers["If-None-Match"] = saved_etag
if saved_last_modified:
    headers["If-Modified-Since"] = saved_last_modified

response = session.get(url, headers=headers, timeout=20)
if response.status_code == 304:
    use_existing_cached_copy()
else:
    response.raise_for_status()
    save_body(response.content)
    save_validators(
        response.headers.get("ETag"),
        response.headers.get("Last-Modified"),
    )

31.5. HTTP/1.1, HTTP/2 и HTTP/3

HTTP/1.1 обычно использует постоянные соединения, но параллельная загрузка ресурсов часто требует нескольких соединений. HTTP/2 вводит потоки и мультиплексирование в одном соединении, а также сжатие заголовков HPACK. HTTP/3 работает поверх QUIC, использующего UDP, и применяет QPACK для сжатия заголовков. Это влияет на сетевую диагностику и производительность, но не меняет семантику HTML-парсинга. Смотри фактический Protocol в DevTools; не делай вывод о версии протокола только по URL.

Не все Python-клиенты поддерживают все версии протокола одинаково. Requests обычно выбирают как простой HTTP-клиент; HTTPX может работать с HTTP/2 при включённой поддержке и установленных дополнительных зависимостях. Поддержка HTTP/3 зависит от конкретного клиента и транспортного backend. Для обычного извлечения данных переход на HTTP/2/3 не обязателен: сначала устрани ошибки и проверь качество ответа.

31.4. Большие файлы и Range

Заголовок Range: bytes=... позволяет запросить часть ресурса. При поддержке сервер вернёт 206 и Content-Range; 200 может означать, что Range проигнорирован; 416 — диапазон недопустим. Для возобновления загрузки нужно проверить, что удалённый файл не изменился: используй ETag/If-Range, сверяй итоговый размер и контрольную сумму. Range не равен chunked transfer encoding.

Практика. На собственном тестовом сервере или публичном ресурсе, разрешающем такие запросы, исследуй: цепочку редиректов, ETag, условный запрос и Range. Сохрани журнал с кодами ответов и объясни каждый переход.
Диагностический принцип: при ошибке сначала классифицируй слой: DNS, соединение, TLS, HTTP, авторизация, формат ответа, JavaScript или парсер. Это сокращает число случайных изменений.

32. Обнаружение страниц и стратегия обхода сайта (crawling)

Scraping извлекает данные из конкретного ответа; crawling обнаруживает, какие страницы нужно запросить. Для каталога, документации или архива публикаций это разные задачи. Не начинай обход с «скачать все ссылки»: сначала определи допустимую область, типы страниц, глубину, максимальное число запросов и критерий остановки.

32.1. Источники URL

  • Стартовые URL и навигационные ссылки.
  • Sitemap XML и sitemap index.
  • RSS/Atom и публичные API.
  • Пагинация, категории, архивы дат.
  • Ссылки из уже собранных записей.

Нормализуй URL аккуратно: разреши относительный адрес через urljoin, убери fragment, проверь схему и host. Не удаляй query-параметры автоматически: они могут задавать страницу, фильтр, язык или идентификатор объекта. Параметры сортировки/аналитики исключай только после подтверждения их семантики.

32.2. Ограниченный обход в ширину

from collections import deque
from urllib.parse import urljoin, urlsplit, urldefrag
import requests
from bs4 import BeautifulSoup

START = "https://example.org/catalog/"
ALLOWED_HOST = "example.org"
MAX_PAGES = 80
MAX_DEPTH = 2

queue = deque([(START, 0)])
seen = set()

while queue and len(seen) < MAX_PAGES:
    url, depth = queue.popleft()
    url, _fragment = urldefrag(url)
    if url in seen:
        continue
    parts = urlsplit(url)
    if parts.scheme != "https" or parts.hostname != ALLOWED_HOST:
        continue
    seen.add(url)

    response = requests.get(url, timeout=(5, 20))
    response.raise_for_status()
    soup = BeautifulSoup(response.content, "html.parser")
    parse_page(url, soup)  # ваша функция, без сетевых побочных эффектов

    if depth < MAX_DEPTH:
        for link in soup.select("a[href]"):
            next_url = urljoin(url, link["href"])
            next_url, _ = urldefrag(next_url)
            if next_url not in seen:
                queue.append((next_url, depth + 1))

Этот пример учебный: для реального обхода добавь задержки и per-host concurrency limit, соблюдай robots.txt и условия источника, обрабатывай redirect safety, повторы, retry budget, canonical URL и checkpoint. Нельзя допускать, чтобы ссылки на бесконечные календари или фильтры генерировали бесконечное пространство URL.

32.3. Sitemap и canonical

Sitemap помогает обнаружить известные адреса, но не гарантирует полноту, актуальность или право на автоматический сбор. Canonical — подсказка о предпочтительном адресе среди вариантов, а не универсальное разрешение удалять query-параметры. Сохраняй исходный URL и канонический URL отдельно, чтобы можно было проверить решение.

Практика. Возьми небольшой сайт, разрешающий автоматическое исследование. Составь карту типов URL, найди sitemap (если существует), запусти обход с лимитом в 30 страниц и глубиной 2. Докажи, что внешние домены и повторные URL не обходятся.

33. Диагностика браузера: Playwright как исследовательский инструмент

Playwright полезен не только для кликов. Он позволяет записать сетевые события, консольные ошибки, снимки DOM, скриншоты и временную линию действий. Это превращает нестабильный сценарий в наблюдаемую последовательность, которую можно анализировать.

33.1. Запись trace и ошибок JavaScript

import asyncio
from pathlib import Path
from playwright.async_api import async_playwright

async def main():
    async with async_playwright() as p:
        browser = await p.chromium.launch(headless=True)
        context = await browser.new_context()
        await context.tracing.start(
            screenshots=True, snapshots=True, sources=True

        page.on("console", lambda msg: print("CONSOLE", msg.type, msg.text))
        page.on("pageerror", lambda exc: print("PAGE ERROR", exc))

33.4. Состояние браузера и HAR

Состояние сайта может распределяться между cookies, localStorage, sessionStorage, IndexedDB, Cache Storage и Service Worker. BrowserContext изолирует контекст, но сохранение cookies/localStorage не обязательно сохраняет всё состояние приложения. Не копируй профиль реального пользователя в проект и не публикуй storage state: в нём могут быть действующие сессионные секреты.

Для диагностики можно записывать HAR — HTTP Archive — с историей запросов и ответов. HAR помогает воспроизводить и исследовать сетевые сценарии, но способен содержать заголовки, cookies, параметры и тела запросов. Перед передачей файла удали секреты и персональные данные. В Playwright изучи запись HAR и route_from_har; используй mock только для тестирования, не для подмены реального источника при отчёте о сборе.

33.3. Локаторы, устойчивые ожидания и контексты

Предпочитай семантические локаторы get_by_role, get_by_label и get_by_test_id, когда они доступны. Locator повторно разрешается в актуальном DOM и поддерживает auto-waiting. Не сохраняй старый ElementHandle на долгое время, если интерфейс перерисовывается. Отдельный BrowserContext изолирует cookies и storage между сценариями.

Практика. На тестовой странице запиши trace, console, pageerror и requestfailed. Найди один клик, который вызывает API-запрос, и извлеки соответствующий JSON. Затем смоделируй таймаут или отсутствующий элемент и определи причину через trace, а не увеличивая sleep наугад.

34. Медиа и сложные ресурсы: srcset, lazy loading, blob и потоки

Медиа может быть спрятано не в очевидном src. Для изображений проверь picture/source/srcset, currentSrc, data-src, CSS background и lazy-loading. Для аудио/видео — audio, video, source, Network → Media и запросы после пользовательского действия.

34.2. Почему blob: URL — не обычная ссылка

blob: URL создаётся в контексте браузера и ссылается на объект, доступный этому origin/context. Это не постоянный адрес файла, который можно передать в Requests. Найди исходный сетевой ответ или manifest/resource, из которого браузер построил Blob. У Media Source Extensions браузер может собирать поток из фрагментов. Исследуй только ресурсы, к которым у тебя есть право доступа.

    response.raise_for_status()

    if not (content_type.startswith("audio/") or content_type == "application/octet-stream"):
        raise ValueError(f"Unexpected MIME type: {content_type}")
    with out.open("wb") as target:
        for chunk in response.iter_content(128 * 1024):
            if not chunk:

            total += len(chunk)

                raise ValueError("Resource too large")
            sha256.update(chunk)
            target.write(chunk)
print("bytes:", total, "sha256:", sha256.hexdigest())

36. Семантическая разметка: JSON-LD, Microdata и RDFa

Сайт может содержать структурированное описание сущности отдельно от визуального HTML. JSON-LD часто находится в <script type="application/ld+json">; Microdata использует атрибуты itemscope/itemprop; RDFa — атрибуты вроде typeof/property. Это полезные сигналы, но их наличие не гарантирует полноту или актуальность.

36.1. Прочитать все JSON-LD блоки

37. Нормализация, сопоставление записей и качество данных

Две строки с разным написанием могут описывать один объект. И наоборот, одинаковое название может относиться к разным объектам. Перед объединением источников определи ключ записи, правила нормализации и поля, которые должны оставаться без изменений.

37.1. Текст и Unicode

import unicodedata
import re

def normalize_text(value: str) -> str:
    value = unicodedata.normalize("NFC", value)
    value = value.replace("\u00a0", " ")
    value = re.sub(r"\s+", " ", value)
    return value.strip()

Не удаляй диакритические знаки, пунктуацию или регистр без понимания предметной области: для имён, кодов, артикулов и языковых данных это может менять смысл. Сохраняй исходное значение в raw-поле рядом с нормализованным.

37.2. Деньги, даты и числовые значения

Строка 1.234,56 € и строка 1,234.56 USD используют разные соглашения. Не заменяй все запятые точками. Определи локаль, валюту, разделитель тысяч и десятичный знак; для денежных сумм используй Decimal, а не float. Даты сохраняй с часовым поясом или нормализуй в UTC, не теряя исходное значение и известную зону.

from decimal import Decimal

37.3. Дедупликация и entity resolution

Начинай с точных ключей: идентификатор источника, canonical URL, GTIN/ISBN/артикул. Если их нет, используй комбинацию признаков и fuzzy matching как подсказку, а не окончательное решение. Сохраняй score, признаки совпадения и статус ручной проверки. Нельзя сливать сущности только по похожему названию.

37.4. Контрольные правила

  • Обязательные поля не пусты.
  • Тип и диапазон значений ожидаемы.
  • URL относится к ожидаемому домену и ресурсу.
  • Уникальный ключ не дублируется.
  • Число записей не падает неожиданно.
  • Доля отсутствующих полей и ошибок отслеживается.

38.3. Идемпотентность

Идемпотентный запуск не создаёт дубликаты и не портит состояние при повторном выполнении. Используй стабильный business key, UPSERT, уникальные ограничения, атомарную запись во временный файл с последующим rename и checkpoint. Не используй порядковый номер строки как устойчивый идентификатор, если порядок источника может измениться.

Практика. Загрузи один и тот же тестовый набор три раза, изменив одно поле в одной записи. После каждого запуска проверь число строк, ключи, изменённые поля и историю. Повторный идентичный запуск не должен создавать новые строки.

39. Инкрементальный сбор и обнаружение изменений

Полный повторный обход сайта часто дорог. Инкрементальный сбор проверяет, что изменилось с прошлого запуска, и обновляет только необходимые записи. Возможные сигналы: ETag, Last-Modified, дата публикации, идентификатор версии, hash нормализованного содержимого.

39.1. Контентный fingerprint

import hashlib
import json

def fingerprint(record: dict) -> str:
    canonical = json.dumps(
        record,
        ensure_ascii=False,
        sort_keys=True,
        separators=(",", ":"),
    )
    return hashlib.sha256(canonical.encode("utf-8")).hexdigest()

Hash следует рассчитывать по полям, которые считаются содержательными. Не включай временную метку самого сбора, иначе запись будет считаться изменённой при каждом запуске. Версионируй правила нормализации: изменение парсера может поменять fingerprint даже при неизменном источнике.

39.2. Состояния объекта

Различай: new — впервые обнаружен; unchanged — fingerprint тот же; updated — содержимое изменилось; missing — не найден в этом обходе; unavailable — сервер не ответил; deleted — есть достаточное основание считать запись удалённой. Не превращай временную ошибку 503 в удаление объекта.

39.3. Выявление исчезнувших объектов

Отсутствие записи в одном запуске ещё не доказывает удаление: пагинация могла оборваться, часть страниц могла вернуть ошибку, а фильтр — изменить состав. Используй завершённый контрольный обход, grace period или несколько подтверждающих наблюдений перед tombstone/deleted статусом.

Практика. Сделай три снимка небольшого каталога: исходный, с изменённой ценой, с исчезнувшей записью. Классифицируй new/unchanged/updated/missing и покажи, как программа отличает отсутствие из-за сбоя от реального удаления.

40. Асинхронность, ограничение нагрузки и backpressure

Асинхронность ускоряет задачи с ожиданием сети, но не делает сервер быстрее и не отменяет лимиты источника. Не запускай тысячи запросов одновременно. Ограничивай in-flight запросы, скорость на домен, общий размер очереди и объём данных в памяти.

40.1. HTTPX AsyncClient с ограниченной конкуренцией

import asyncio
import httpx

LIMIT = 4
semaphore = asyncio.Semaphore(LIMIT)

async def fetch_one(client: httpx.AsyncClient, url: str):
    async with semaphore:
        response = await client.get(url)
        response.raise_for_status()
        return {"url": str(response.url), "body": response.text}

async def main(urls: list[str]):
    limits = httpx.Limits(max_connections=LIMIT, max_keepalive_connections=2)
    timeout = httpx.Timeout(20.0, connect=5.0)
    async with httpx.AsyncClient(
        timeout=timeout, limits=limits, follow_redirects=True
    ) as client:
        results = await asyncio.gather(
            *(fetch_one(client, url) for url in urls),
            return_exceptions=True,
        )
    for result in results:
        if isinstance(result, Exception):
            print("FAILED", repr(result))
        else:
            process(result)

# asyncio.run(main(urls))

Для небольшого списка этот пример понятен. Для миллионов URL не создавай миллионы задач через один gather: применяй ограниченную очередь asyncio.Queue, фиксированное число workers, потоковую запись результата и producer-consumer схему. Так backpressure не даст очереди бесконечно расти.

40.2. План повторов и 429

Retry нужен для временных ошибок, но не для каждого исключения. Не повторяй бесконечно 400, 401, 403 или ошибку парсинга. Для 429/503 проверь Retry-After, уменьши скорость, добавь jitter и общий retry budget. Повтор POST/операции изменения состояния безопасен не всегда: учитывай идемпотентность метода и API.

40.3. Скорость и обратное давление

  • Ограничивай число одновременных запросов отдельно для каждого host.
  • Добавляй задержки и соблюдай документированные rate limits.
  • Не скачивай следующий пакет быстрее, чем хранилище успевает записывать предыдущий.
  • Используй bounded queue и прекращай producer при перегрузке.
  • Отслеживай latency, error rate, queue depth и объём памяти.
Практика. Создай очередь из 100 тестовых URL и 3 worker-задачи. Измерь максимальное число одновременных запросов, частоту ошибок и время завершения. Сравни с неограниченным запуском на локальном тестовом сервере, а не на чужом сайте.

41. Scrapy на практике: spider, middleware, pipeline и AutoThrottle

Scrapy полезен, когда нужно обходить много страниц по графу ссылок, а не просто запросить несколько URL. Его архитектура разделяет Spider, Engine, Scheduler, Downloader, Middleware, Item Pipeline и Feed Export. Это позволяет вынести повторяющееся поведение в общий компонент.

41.1. Минимальный spider

import scrapy

class CatalogSpider(scrapy.Spider):
    name = "catalog"
    allowed_domains = ["example.org"]
    start_urls = ["https://example.org/catalog/"]

    custom_settings = {
        "ROBOTSTXT_OBEY": True,
        "CONCURRENT_REQUESTS_PER_DOMAIN": 2,
        "DOWNLOAD_DELAY": 1.0,
        "AUTOTHROTTLE_ENABLED": True,
        "AUTOTHROTTLE_START_DELAY": 1.0,
        "AUTOTHROTTLE_MAX_DELAY": 20.0,
        "FEEDS": {"data/items.jsonl": {"format": "jsonlines"}},
    }

    def parse(self, response):
        for card in response.css("article.card"):
            yield {
                "title": card.css("h2::text").get(default="").strip(),
                "url": response.urljoin(card.css("a::attr(href)").get()),
            }

        next_page = response.css("a.next::attr(href)").get()
        if next_page:
            yield response.follow(next_page, callback=self.parse)

41.2. Pipelines и middleware

Item Pipeline — место для очистки, проверки обязательных полей, дедупликации и сохранения. Downloader Middleware работает ближе к HTTP-слою: заголовки, таймауты, обработка отдельных ответов и разрешённая авторизация. Не помещай в spider логику, которая должна одинаково применяться ко всем источникам.

41.3. Возобновление, кэш и медиа

Изучи JOBDIR для сохранения состояния задания, HTTP cache для разработки, AutoThrottle для динамического ограничения скорости, SitemapSpider для sitemap-ориентированного обхода, FilesPipeline/ImagesPipeline для официально доступных медиа и feed exports для JSON/CSV/XML. Настройки проверяй по актуальной документации своей версии Scrapy.

42.3. Принцип безопасного логирования

Логируй run_id, source_id, URL без секретных query-параметров, статус, время и категорию ошибки. Не записывай пароли, cookies, Authorization, полные персональные записи или содержимое закрытых страниц. Сырые сетевые дампы храни ограниченное время и с контролем доступа.

Практика. Напиши 8 тестов для парсера: нормальная запись, отсутствующее имя, относительная ссылка, неправильный тип, дубликат, пустой список, повреждённый JSON и неожиданный HTML. Сформируй JSON-отчёт каждого запуска с метриками качества.

43. Безопасность и приватность данных

Сборщик обрабатывает и сетевые ответы, и недоверенные данные. Безопасность должна быть частью архитектуры, а не исправлением в конце. Разделяй техническую возможность получить данные и право их собирать, хранить, объединять и использовать.

43.1. Защита HTTP-клиента

  • Разрешай только ожидаемые схемы и хосты; проверяй каждый redirect.
  • Не отправляй секреты на другой origin автоматически.
  • Ограничивай время, размер ответа, число перенаправлений и глубину архива.
  • Защищай внутренние адреса и localhost от SSRF.
  • Не исполняй скачанные скрипты, макросы и бинарные файлы.
  • Для ZIP проверяй traversal и суммарный распакованный размер.

43.2. Персональные и чувствительные данные

До сбора определи, нужны ли персональные данные вообще. Минимизируй поля, задавай цель и срок хранения, ограничивай доступ, не объединяй данные для нового назначения без проверки правового основания. Для данных пользователей учитывай применимые требования приватности и локальное законодательство. Учебный пример не является юридической консультацией.

43.3. Не путай доступность с разрешением

Публично видимая страница не означает, что массовое копирование, повторная публикация или построение профилей разрешено. Проверяй официальные API, условия, лицензии, robots.txt, ограничения частоты и права на контент. Не обходи CAPTCHA, MFA, paywall, DRM, антибот-защиту или отказ в доступе; при необходимости получи разрешённый API-доступ или останови сбор.

Практика. Для выбранного проекта напиши data protection note: какие поля собираются, зачем, откуда, на каком основании, кто имеет доступ, сколько хранятся и как удаляются. Проведи threat-model: SSRF, утечка токена, опасный архив, избыточный сбор и случайный публичный экспорт.

44. Планирование, развёртывание и эксплуатация

Автоматизация может запускаться вручную, по расписанию или как постоянный worker. Выбор зависит от частоты, объёма, требований к возобновлению и допустимой задержки. Для начала часто достаточно Windows Task Scheduler, cron или systemd timer. Очередь задач и оркестратор нужны не каждому проекту.

44.1. Что хранить между запусками

  • Конфигурацию источника и версию парсера.
  • Cursor/page/checkpoint и статус каждой задачи.
  • Валидаторы HTTP и fingerprint последней записи.
  • Счётчики ошибок и время последнего успешного полного прохода.
  • Версию схемы и миграции хранилища.

44.2. Контейнеризация

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY collector ./collector
ENV PYTHONUNBUFFERED=1
CMD ["python", "-m", "collector", "--output", "/data"]

Для реального проекта закрепи версии зависимостей lock-файлом, добавь непривилегированного пользователя и health check. Подключи отдельный volume для /data: пересоздание контейнера не должно удалять базу. Секреты передавай через секрет-хранилище или безопасные переменные окружения, а не включай в образ.

44.3. Планировщик и защита от параллельного запуска

Если предыдущий сбор ещё выполняется, новый запуск не должен бесконтрольно стартовать второй раз. Используй lock/lease, уникальный run_id и таймаут выполнения. После сбоя lock должен истекать или освобождаться безопасно. Предусмотри уведомление о неуспешном запуске и автоматическое сохранение отчёта.

Практика. Запусти сборщик по расписанию на локальной машине. Имитируй отключение сети, повторный запуск и одновременный старт двух экземпляров. Убедись, что данные не теряются и конкурентные процессы не портят одну задачу.

  8. Только затем выбирай архитектуру и масштабируй.

49. Selenium, WebDriver и альтернативы Playwright

Playwright — сильный вариант по умолчанию для новых Python-проектов, но не единственный. Selenium важен для существующих тестовых инфраструктур, браузерных ферм, корпоративных систем и сценариев, где уже используются WebDriver/Grid. Puppeteer полезен прежде всего в JavaScript/TypeScript-проектах. Выбирать инструмент нужно по требованиям, а не по популярности.

49.1. Модель Selenium WebDriver

WebDriver управляет браузером через стандартизированный интерфейс. Сценарий отправляет команды драйверу, драйвер взаимодействует с браузером. Для Python используется пакет selenium. В новых проектах применяй явные ожидания, а не фиксированные задержки.

from selenium import webdriver
from selenium.webdriver.common.by import By
from selenium.webdriver.support.ui import WebDriverWait
from selenium.webdriver.support import expected_conditions as EC

options = webdriver.ChromeOptions()
options.add_argument("--headless=new")

driver = webdriver.Chrome(options=options)
try:
    driver.get("https://example.com")
    heading = WebDriverWait(driver, 10).until(
        EC.visibility_of_element_located((By.CSS_SELECTOR, "h1"))
    )
    print(heading.text)
finally:
    driver.quit()

Selenium Grid распределяет браузерные сессии по удалённым узлам. Это полезно, когда нужны разные браузеры, ОС или параллельные тестовые агенты. Для одного личного сборщика Grid обычно избыточен. Не запускай десятки браузеров до измерения реальной потребности.

Правило: не переписывай работающий Playwright-сценарий на Selenium только ради «универсальности». Добавляй второй инструмент, когда есть конкретная совместимость или инфраструктурная причина.

50. CDP, WebDriver BiDi и исследование сетевого трафика

Браузерные библиотеки высокого уровня скрывают детали протокола. Иногда для диагностики нужно увидеть события ниже уровня DOM: запросы, ответы, консоль, ошибки JavaScript, кадры WebSocket и тайминги. Для Chromium применяется Chrome DevTools Protocol (CDP); WebDriver BiDi создаётся как стандартизированный двунаправленный протокол браузерной автоматизации.

50.1. CDP через Playwright

В Playwright для Python CDP-сессия создаётся для Chromium. Это низкоуровневый инструмент; команды и события зависят от версии Chromium. Не строй весь сборщик на недокументированных внутренних командах, если высокоуровневый API решает задачу.

import asyncio
from playwright.async_api import async_playwright

async def main():
    async with async_playwright() as p:
        browser = await p.chromium.launch()
        page = await browser.new_page()
        client = await browser.new_cdp_session(page)
        await client.send("Network.enable")

        client.on("Network.responseReceived", lambda event: print(
            event["response"]["status"],
            event["response"]["url"]
        ))
        await page.goto("https://example.com")
        await browser.close()

asyncio.run(main())

50.2. WebDriver BiDi

BiDi позволяет получать события от браузера по двунаправленному соединению. Изучай доступные высокоуровневые API Selenium и матрицу поддержки конкретных браузеров. Наличие стандарта не означает, что каждая функция уже одинаково реализована во всех браузерах.

50.3. HAR, mitmproxy и Wireshark

  • HAR — запись HTTP-обмена браузера; полезна для воспроизведения и сравнения запросов.
  • mitmproxy — локальный HTTP(S)-прокси с просмотром и сохранением потоков; сертификат доверия нужно устанавливать только в контролируемой тестовой среде.
  • Wireshark — анализ сетевых пакетов и соединений; при HTTPS без ключей/доступа к расшифровке содержимое обычно не видно.
# Запустить mitmweb для локальной отладки
mitmweb --listen-host 127.0.0.1 --listen-port 8080

# Сохранить трафик в файл из терминального режима
mitmdump --listen-host 127.0.0.1 --listen-port 8080 -w session.mitm
Безопасность: не устанавливай перехватывающий CA-сертификат на чужие устройства и не перехватывай чужие учётные данные. Исследуй только собственные приложения, тестовые стенды или трафик, на обработку которого у тебя есть явное разрешение.
Практика. Запиши HAR собственного тестового сайта, найди один запрос данных, сравни URL, метод, статус, заголовки, payload и initiator. Затем повтори наблюдение через mitmproxy на localhost и объясни различие между HAR и сетевым захватом пакетов.

51.3. IndexedDB, Service Workers и HAR

IndexedDB исследуется через Application в DevTools или соответствующие JavaScript API. В Playwright сохранение состояния браузера поддерживает IndexedDB в актуальных версиях API; проверь версию установленного Playwright и параметры storage_state. HAR помогает воспроизвести HTTP-обмен, но Service Worker может влиять на перехват и replay. При сравнительных тестах полезно отдельно проверять профиль с Service Worker и без него.

# Playwright: сохранить cookies и localStorage;

# В диагностическом тесте можно создать контекст без Service Worker:

Защита состояния. Файлы storage state, HAR и дампы IndexedDB могут содержать сессионные идентификаторы и персональные данные. Не коммить их в Git, не публикуй и ограничивай срок хранения. Для воспроизводимых тестов предпочитай тестовые аккаунты.
Практика. На собственном локальном приложении создай значение в localStorage, запись в IndexedDB и Service Worker-кэш. Сравни холодный запуск, повторный запуск и новый browser context. Определи, какие данные сохраняются между ними.

53. gRPC, Protocol Buffers, SOAP, OData и бинарные форматы

Не каждый сетевой интерфейс является REST/JSON. Если в Network виден необычный content type, бинарное тело, XML envelope или gRPC-вызов, сначала определи протокол. Не пытайся бездумно декодировать байты как UTF-8: формат может быть бинарным, сжатым или содержать фреймирование протокола.

53.1. gRPC и Protocol Buffers

gRPC описывает сервисы и методы, а Protobuf — структуру сообщений. Для Python обычно нужны файл .proto, сгенерированные классы и stub-клиент. Простого URL и Requests недостаточно: важны HTTP/2, тип контента, сериализация и контракт сервиса.

# Типовой клиент после генерации Python-кода из .proto:
import grpc
import catalog_pb2
import catalog_pb2_grpc

channel = grpc.insecure_channel("localhost:50051")  # только локальный учебный стенд
stub = catalog_pb2_grpc.CatalogStub(channel)
response = stub.GetItem(catalog_pb2.GetItemRequest(id="42"))
print(response)

Для реального сервиса используй TLS, проверку сертификата и официальный способ авторизации. Reflection может быть отключён; отсутствие reflection не означает, что сервис недоступен — но без схемы нельзя надёжно интерпретировать сообщения.

53.2. SOAP

SOAP использует XML-конверт и определённую структуру сообщения; описание сервиса часто доступно через WSDL. В HTTP-запросе могут использоваться специальные заголовки и SOAPAction. XML следует разбирать безопасным парсером с отключёнными внешними сущностями (XXE).

import requests

endpoint = "https://example.test/service"  # замени на разрешённый endpoint
soap_body = """<?xml version="1.0"?>
<soap:Envelope xmlns:soap="http://www.w3.org/2003/05/soap-envelope">
  <soap:Body>
    <GetItem xmlns="urn:example"><Id>42</Id></GetItem>
  </soap:Body>
</soap:Envelope>"""

response = requests.post(
    endpoint,
    data=soap_body.encode("utf-8"),
    headers={"Content-Type": "application/soap+xml; charset=utf-8"},
    timeout=(5, 20),
)
response.raise_for_status()
print(response.text[:500])

53.3. OData

OData — стандартизированный протокол доступа к данным. Его URL-конвенции могут поддерживать фильтрацию, выбор полей, сортировку, расширение связанных сущностей и постраничный переход. Например, параметры $select, $filter, $orderby, $top и $skip нужно изучить по документации конкретного сервиса.

import requests

url = "https://services.odata.org/V4/OData/OData.svc/Products"
params = {
    "$select": "ID,Name,Price",
    "$top": 20,
    "$orderby": "ID",
}
response = requests.get(url, params=params, timeout=20)
response.raise_for_status()
data = response.json()
print(data)

53.4. MessagePack, multipart и content types

  • MessagePack — компактная бинарная сериализация структур данных; Python-пакет msgpack.
  • multipart/form-data — отправка полей и файлов в одном теле запроса; в Requests используется параметр files=.
  • Protocol Buffers — схема и сериализация, а не просто формат «JSON в бинарном виде».
  • Content-Type и Content-Encoding — разные понятия: первое описывает тип содержимого, второе — способ кодирования/сжатия представления.
Практика. На локальных или публичных учебных сервисах определи по документации и Network, какой протокол используется. Для OData сформируй запрос с выбором полей и сортировкой. Для собственного SOAP/gRPC стенда прочитай схему и создай типизированный запрос. Не делай вывод о формате только по расширению URL.

54. OAuth 2.0, OpenID Connect, SAML, JWT, MFA и WebAuthn

Авторизация — один из самых сложных участков автоматизации. Сначала нужно понять, кто проверяет личность пользователя, кто выдаёт разрешения и как приложение подтверждает запросы. Используй только свои тестовые аккаунты, официальные API и разрешённые сценарии. Не пытайся обходить MFA, CAPTCHA, защиту учётной записи или ограничения доступа.

54.2. Разрешённый OAuth/OIDC-процесс

  1. Проверь документацию провайдера и зарегистрируй приложение законным способом.
  2. Используй рекомендованный flow; для публичных клиентов обычно рассматривается Authorization Code с PKCE.
  3. Запрашивай минимальные scopes.
  4. Проверяй issuer, audience, срок действия и подпись токена там, где это требуется.
  5. Обновляй токены только через предусмотренный token endpoint.
  6. Не записывай access/refresh tokens в логи и не помещай их в публичный репозиторий.

54.3. Автоматизация сессии — только для собственного аккаунта

Для повторных UI-тестов допустимо сохранять состояние тестового браузерного контекста. Но такой файл эквивалентен секрету доступа. Для производственного сбора предпочитай официальный OAuth/API-интерфейс, а не постоянное копирование cookies из пользовательского браузера.

Граница применения. Нельзя превращать этот раздел в инструкции по краже токенов, обходу второго фактора, подделке assertions или использованию чужой сессии. При доступе к данным стороннего сервиса используй его официальный API и выданные разрешения.
Практика. На локальном OAuth/OIDC demo-provider нарисуй sequence diagram: браузер, клиент, authorization server, token endpoint и resource server. Отдельно подпиши, чем access token отличается от ID token и почему простое декодирование JWT не проверяет его подлинность.

55. Извлечение статей и документов: специализированные парсеры

У статей, новостей и блогов есть особая проблема: нужно отделить основной текст от меню, рекламы, рекомендаций и футера. Для этого существуют специализированные extractors. Они не заменяют crawler: сначала нужно обнаружить разрешённые URL, скачать страницу, а затем извлечь основное содержимое.

55.1. Trafilatura для основного текста

import requests
import trafilatura

url = "https://example.com/article"
response = requests.get(url, timeout=20)
response.raise_for_status()
html = response.text

result = trafilatura.extract(
    html,
    output_format="json",
    with_metadata=True,
    include_links=False,
)
print(result)

55.2. Parsel, Readability и Selectolax

Trafilatura подходит для основного текста и метаданных. Readability-подобные алгоритмы пытаются выделять читаемую область. Parsel нужен для точных структурированных полей через CSS/XPath/JMESPath. Selectolax помогает быстро разбирать большое число HTML-документов. Для каждого набора страниц измеряй precision и recall на вручную размеченной выборке.

55.3. Документы и текстовые слои

  • PDF с текстовым слоем: PyMuPDF, pdfplumber, pypdf — выбор зависит от таблиц, геометрии и потребности в метаданных.
  • Сканированный PDF: рендер страницы и OCR; проверяй язык, качество и координаты распознанных блоков.
  • DOCX: абзацы, таблицы, заголовки, hyperlinks и metadata.
  • XLSX: листы, формулы, значения, объединённые ячейки и скрытые листы.
  • EPUB: ZIP-контейнер с XHTML и метаданными; соблюдай лицензию и ограничения доступа.
Проверяй границы. Извлечение основного текста может потерять подписи к изображениям, списки, таблицы и боковые примечания. Храни исходный HTML/документ вместе с нормализованным результатом, когда это разрешено политикой хранения.
Практика. Возьми 20 статей с разрешённого источника, вручную разметь основной текст и метаданные, сравни результат Trafilatura и собственного селектора. Составь таблицу ошибок: пропущенные абзацы, лишнее меню, неверная дата, неверный автор.

57. HLS, MPEG-DASH, MSE и сегментированные медиапотоки

Видео на сайте может быть не одним MP4-файлом. Браузер может загружать манифест, выбирать вариант качества и последовательно получать сегменты. Для HLS часто используется playlist M3U8; для MPEG-DASH — MPD manifest. Media Source Extensions (MSE) позволяют приложению добавлять сегменты в SourceBuffer.

57.1. Как распознать поток

  1. Открой Network и включи фильтр Media.
  2. Посмотри типы и имена ресурсов: .m3u8, .mpd, .ts, .m4s, аудио- и видео-сегменты.
  3. Открой вкладку Initiator и выясни, какой скрипт инициирует запросы.
  4. Сохрани манифест и изучи относительные URL, варианты качества, таймкоды и сегменты.
  5. Проверь, есть ли отдельные аудиодорожки, субтитры и live-обновление манифеста.

57.2. Разбор доступного потока

Для собственных или явно разрешённых ресурсов можно использовать FFmpeg. Он умеет читать многие HLS/DASH-манифесты и собирать медиапоток. Команда ниже не обходит DRM, авторизацию или иные ограничения; входной URL должен быть доступен тебе законным способом.

# Информация о дорожках и кодеках
ffprobe -hide_banner -i "https://media.example.test/playlist.m3u8"

# Перемультиплексировать доступный поток без повторного кодирования
ffmpeg -i "https://media.example.test/playlist.m3u8" -c copy output.mp4

57.3. Что может пойти не так

  • Манифест содержит относительные адреса, которые нужно разрешать относительно URL самого манифеста.
  • Live-плейлист меняется во времени; конечного списка сегментов может не быть.
  • Сегменты могут требовать заголовки, cookies или токены согласно разрешённому доступу.
  • Раздельные аудио/видео дорожки могут требовать объединения и синхронизации.
  • DRM — отдельная система защиты контента; курс не обучает обходить DRM или извлекать ключи.
Практика. Создай HLS-поток из собственного тестового видео с помощью FFmpeg. Исследуй manifest, варианты качества, сегменты и субтитры. Затем скачай только свой поток и сравни итоговый файл с оригиналом по длительности, дорожкам и контрольной сумме после декодирования.

58. Сложные браузерные рабочие процессы и устойчивые сценарии

Реальные задачи часто состоят не из одного клика, а из последовательности состояний: открыть каталог, выбрать фильтр, раскрыть карточку, переключить вкладку, дождаться API-ответа, скачать документ и вернуться к списку. Надёжный сценарий моделирует состояния и проверяет результат каждого перехода.

58.1. Page Object и конечный автомат

Page Object хранит селекторы и действия для конкретной страницы. Для длинных процессов полезно описывать состояние явно: START → FILTERED → DETAIL → DOWNLOADED. Каждый шаг должен иметь предусловия, ожидаемый переход и восстановление при ошибке.

from enum import Enum, auto

class State(Enum):
    START = auto()
    FILTERED = auto()
    DETAIL = auto()
    DOWNLOADED = auto()

async def run_flow(page):
    state = State.START

    await page.get_by_label("Category").select_option("books")
    await page.get_by_role("button", name="Apply").click()
    await page.get_by_role("heading", name="Books").wait_for()
    state = State.FILTERED

    await page.get_by_role("link", name="Open first item").click()
    await page.get_by_test_id("item-detail").wait_for()
    state = State.DETAIL

    async with page.expect_download() as download_info:
        await page.get_by_role("button", name="Download").click()
    download = await download_info.value
    await download.save_as("downloads/item.pdf")
    state = State.DOWNLOADED
    return state

60.3. Универсальный алгоритм решения задачи

  1. Сформулируй результат. Какие конкретные поля, файлы и связи нужны? Как будет проверена полнота?
  2. Исследуй источник. Проверь публичную документацию, условия доступа, HTML, Network, редиректы и поведение после действий.
  3. Определи канал. API, HTML, браузерный DOM, поток, документ или их комбинация.
  4. Сделай минимальный эксперимент. Получи 3–10 записей и сравни их с источником вручную.
  5. Зафиксируй контракт. Схема, типы, обязательные поля, правила пагинации и условия остановки.
  6. Построй устойчивый сбор. Timeouts, ограничение параллельности, retry с backoff, checkpoint, dedupe.
  7. Сохраняй provenance. Источник, URL, время сбора, статус, версия парсера и контрольная сумма ресурса.
  8. Проверяй качество. Полнота, уникальность, диапазоны, связи, свежесть и аномалии.
  9. Организуй повторное выполнение. Инкрементальность, idempotency, логирование и сигнализация сбоев.
  10. Документируй решение. Почему выбран инструмент, что может сломаться и как диагностировать.

60.4. Итоговый проект

Создай систему сбора из трёх разрешённых источников разного типа: один статический HTML-каталог, одно JavaScript-приложение с публичным API и один набор документов. Система должна собирать записи по расписанию, скачивать относящиеся к ним файлы, нормализовать поля, сохранять результат в SQLite и Parquet, находить изменения между запусками и формировать отчёт качества.

  • У каждого адаптера — отдельные тесты на сохранённых fixtures.
  • Все HTTP-запросы имеют таймауты и ограничение скорости.
  • Повторный запуск не создаёт дубликаты.
  • Ошибки одного источника не уничтожают результаты остальных.
  • В отчёте есть число обнаруженных, загруженных, пропущенных и ошибочных объектов.
  • Секреты, персональные данные и session state не попадают в Git и обычные логи.
Критерий завершения: ты способен самостоятельно исследовать незнакомый, доступный для автоматизированной обработки источник, доказать корректность выбранного метода, построить воспроизводимый сбор и объяснить ограничения решения. Это и есть практическая универсальность — не один магический скрипт для всего интернета, а системный способ решать разные задачи.
Финальная защита проекта. Подготовь README, диаграмму архитектуры, схему данных, образцы исходных ответов, результаты тестов, отчёт полноты и список известных ограничений. Другой разработчик должен суметь развернуть систему и повторить сбор по инструкции.

61. Современные HTTP-клиенты: HTTPX, aiohttp, curl_cffi и streaming

Это не взаимозаменяемые «улучшенные requests»: выбор зависит от протокола, нагрузки, потока данных и диагностики.

61.1. Переиспользуй клиент и ограничивай соединения

Создавай один клиент на логическую сессию, а не новый на каждый URL. Явно задай connect/read/write/pool timeout, лимиты соединений, проверку TLS и redirect policy. Таймауты должны быть конечными. Повторяй только безопасные операции и только по ограниченной политике.

import asyncio
from pathlib import Path
import httpx

async def download(url: str, destination: Path) -> None:
    timeout = httpx.Timeout(30.0, connect=8.0)
    limits = httpx.Limits(max_connections=8, max_keepalive_connections=4)
    async with httpx.AsyncClient(
        timeout=timeout,
        limits=limits,
        follow_redirects=True,
        headers={"User-Agent": "ResearchCollector/1.0 (contact: you@example.org)"},
    ) as client:
        async with client.stream("GET", url) as response:
            response.raise_for_status()
            content_type = response.headers.get("content-type", "")
            if content_type.startswith("text/html"):
                raise ValueError("Expected a file, received HTML")
            destination.parent.mkdir(parents=True, exist_ok=True)
            with destination.open("wb") as output:
                async for chunk in response.aiter_bytes(64 * 1024):
                    output.write(chunk)

async def main():
    await download("https://example.org/data.bin", Path("downloads/data.bin"))

if __name__ == "__main__":
    asyncio.run(main())

61.2. Потоковое чтение и WebSocket

Не вызывай response.content, response.json() или response.text() для многогигабайтного ответа без оценки памяти: многие удобные методы читают тело целиком. Используй итерацию по chunks. Для aiohttp WebSocket-клиент подключается через ClientSession.ws_connect(); отделяй чтение сообщений от записи, учитывай ping/pong, закрытие соединения, reconnect и backoff.

О curl_cffi. Имитация TLS/HTTP fingerprint может использоваться для совместимости и диагностики легитимного клиента. Она не превращает запрещённый endpoint в разрешённый и не должна применяться для обхода CAPTCHA, paywall, MFA, доступа или rate limits. При отказе сервера сначала выясни причину и используй официальный API/разрешённый способ.
Практика. Реализуй один и тот же запрос тремя способами: requests, httpx и aiohttp. Сравни время, объём памяти, поведение при timeout, redirect и 429. Затем скачай тестовый бинарный файл потоково и проверь размер и SHA-256.
Критерий: ты можешь объяснить, почему выбран конкретный клиент, как ограничены соединения и что произойдёт при обрыве передачи.

62.1. Hydration и RSC — не одно и то же

Hydration связывает серверно отрисованный HTML с клиентскими обработчиками. React Server Components добавляют границу между серверной и клиентской частями приложения и передают представление дерева компонентов. В Next.js это может сопровождаться RSC payload и streaming. Nuxt/Vue имеют собственные механизмы SSR и hydration. Не делай вывод о доступности данных только по наличию HTML.

62.2. Алгоритм исследования

  1. Сохрани исходный HTML через View Source и обычный HTTP-запрос.
  2. Сравни с DOM после выполнения JavaScript.
  3. Проверь встроенные JSON/JSON-LD и script data blocks.
  4. Запиши Network при первой загрузке и при переходе между страницами.
  5. Отдельно проверь hydration, lazy loading и streaming.
  6. Ищи документированный API или серверный endpoint; не привязывайся к недокументированному формату фреймворка без необходимости.
from bs4 import BeautifulSoup
import json
import requests

url = "https://example.org/catalog"
response = requests.get(url, timeout=20)
response.raise_for_status()
soup = BeautifulSoup(response.text, "html.parser")

# Сначала исследуем публичные структурированные данные.
for node in soup.select('script[type="application/ld+json"]'):
    try:
        data = json.loads(node.string or node.get_text())
    except json.JSONDecodeError:
        continue
    print("JSON-LD type:", type(data).__name__)

# Сохраняем исходный HTML для воспроизводимого анализа.
open("page-source.html", "w", encoding="utf-8").write(response.text)
print("status:", response.status_code, "final URL:", response.url)
Не делай так: не считай внутренние RSC/Flight chunk identifiers, webpack chunks или приватные hydration internals стабильным API. Они могут меняться между сборками. Если endpoint не документирован, ограничь использование разрешённым исследованием, добавь тесты и fallback на пользовательски наблюдаемое содержимое.
Практика. Возьми учебное приложение на Next.js или Nuxt. Сравни View Source, DOM после hydration и сетевые ответы. Отметь, какие поля видны в HTML, какие приходят из API и какие вообще не отправляются браузеру.
Критерий: ты умеешь классифицировать страницу по модели рендеринга и выбираешь источник данных, не предполагая, что вся информация обязана быть в DOM.

63.1. Обнаружение контракта

Проверь официальную документацию, developer portal, OpenAPI/Swagger endpoint, HTML-ссылки на спецификацию и заголовки ответов. Контракт может быть неполным или устаревшим: сверяй его с реальными ответами. Не запускай неизвестные операции записи только ради исследования.

import httpx

endpoint = "https://api.example.org/rpc"
payload = {
    "jsonrpc": "2.0",
    "method": "catalog.getItem",
    "params": {"itemId": "demo-123"},
    "id": 1,
}

response = httpx.post(endpoint, json=payload, timeout=20)
response.raise_for_status()

if message.get("id") != payload["id"]:
    raise ValueError("JSON-RPC response id does not match request")

    raise RuntimeError(f"RPC error: {message['error']}")

    raise ValueError("JSON-RPC response has no result")
print(message["result"])

63.2. Валидация ответа по схеме

Сохраняй исходный JSON отдельно от нормализованной модели. Проверяй обязательные поля, типы, диапазоны, nullable и неизвестные поля. Различай транспортную ошибку, ошибку протокола и ошибку бизнес-данных. Для больших API изучи генерацию клиента из OpenAPI, но не принимай автоматически сгенерированный клиент за доказательство корректности сервера.

Актуальность версий. В курсе указаны опубликованные версии OpenAPI 3.2.1 и Arazzo 1.1.0; AsyncAPI следует изучать по текущей стабильной спецификации 3.x. В рабочих проектах фиксируй версию спецификации и валидатора, а не полагайся на слово latest.
Практика. Найди публичный OpenAPI документ. Построй таблицу endpoint → method → параметры → auth → response schema. Сгенерируй тестовый клиент или напиши небольшой ручной клиент и проверь минимум три успешных и три ошибочных ответа.
Критерий: ты умеешь понять не только куда отправлять запрос, но и что запрос означает, какую последовательность вызовов он требует и как проверить ответ.

64. WebTransport, WebRTC, QUIC и современные realtime-каналы

WebSocket, WebTransport и WebRTC решают разные задачи. Их нельзя считать тремя способами получить одну и ту же страницу.

ТехнологияМодельКогда встретишь

64.1. WebTransport — не просто новый WebSocket

WebTransport предоставляет несколько потоков, однонаправленные потоки и datagrams с различными гарантиями доставки. Он использует HTTP/3 и защищённый контекст. Поддержка браузеров и серверная реализация должны проверяться по конкретной платформе. Сам факт поддержки API в браузере не означает, что произвольный сайт использует его.

// Запускать в консоли DevTools на собственном тестовом сайте.
const report = {
  webSocket: typeof WebSocket !== "undefined",
  webTransport: typeof WebTransport !== "undefined",
  webRTC: typeof RTCPeerConnection !== "undefined",
};
console.table(report);

// Подключение возможно только к известному endpoint,
// предназначенному сервером для WebTransport.
async function openTransport(authorizedEndpoint) {
  if (!("WebTransport" in window)) {
    throw new Error("WebTransport is not supported in this browser");
  }
  const transport = new WebTransport(authorizedEndpoint);
  await transport.ready;
  return transport;
}

64.2. WebRTC требует signalling

Для WebRTC приложение обменивается SDP/ICE параметрами через отдельный signalling-механизм; затем ICE выбирает маршрут, при необходимости с STUN/TURN. DataChannel передаёт произвольные данные между peer, но это не HTTP endpoint, который можно просто опросить Requests. Для Python могут применяться реализации вроде aiortc, если ты разрабатываешь или легитимно интегрируешься с соответствующей системой.

64.3. Что должен сделать исследователь

  1. Зафиксировать тип соединения и инициатора.
  2. Понять, какой канал несёт именно нужные данные: текстовые события, бинарные кадры, audio/video или signalling.
  3. Проверить формат payload, частоту сообщений, backpressure и reconnect.
  4. Не перехватывать чужую коммуникацию и не обходить требования к авторизации.
Практика. Создай локальные демонстрации WebSocket, WebTransport (если среда поддерживается) и WebRTC DataChannel. Запиши различия в установлении соединения, двусторонней передаче, надёжности и диагностике.
Критерий: ты можешь распознать транспорт и понять, является ли он вообще подходящим источником для задачи сбора данных.

65. AI Browser Automation: Browser Use, Stagehand и агентные сценарии

AI browser agents — надстройка над браузерной автоматизацией: модель получает наблюдение о странице, выбирает действие, получает новый результат и повторяет цикл. Browser Use предоставляет Python-ориентированный подход; Stagehand — AI-powered browser automation, преимущественно в TypeScript/Node.js экосистеме. Это не замена Playwright для всех случаев.

Browser Use / агентМожет планировать действия по естественно-языковой задачеНестабильность, стоимость модели, непредсказуемые действия

65.1. Агент должен иметь границы

  • Задавай узкую задачу и конечные критерии остановки.
  • Передавай только необходимый доступ и не помещай секреты в prompt.
  • Считай текст страницы недоверенными данными: инструкции сайта не должны менять системную задачу агента.
  • Запрещай агенту произвольные платежи, публикации, отправку форм и изменение аккаунта без явного подтверждения человека.
  • Сохраняй trace, скриншоты и доказательства для каждого извлечённого поля.
  • Валидируй результат по схеме; модельная уверенность не заменяет проверку.
# Пример Browser Use: API быстро развивается — закрепи версию пакета
# и проверь сигнатуру Agent/LLM по документации установленной версии.
import asyncio
import os
from browser_use import Agent
from langchain_openai import ChatOpenAI

async def main():
    if not os.getenv("OPENAI_API_KEY") or not os.getenv("BROWSER_AGENT_MODEL"):
        raise RuntimeError("Set OPENAI_API_KEY and BROWSER_AGENT_MODEL in the environment")

    agent = Agent(
        task=(
            "Открой публичный учебный каталог, извлеки первые 5 названий "
            "и URL. Ничего не покупай, не входи в аккаунт и не отправляй формы. "
            "Верни только структурированный список с источниками."
        ),
        llm=ChatOpenAI(model=os.environ["BROWSER_AGENT_MODEL"]),
    )
    result = await agent.run()
    print(result)

if __name__ == "__main__":
    asyncio.run(main())

65.2. Детерминированная проверка после агента

После агентского этапа открой источник обычным HTTP-клиентом или Playwright и повторно проверь URL, заголовок, идентификатор и другие важные поля. Для критичных данных сохраняй фрагмент текста/DOM, URL, timestamp и результат проверки. Там, где структура стабильна, замени agent action на явный Playwright locator.

Риск prompt injection. Страница может содержать текст «игнорируй предыдущие инструкции» или просить раскрыть секреты. Для агента это содержимое страницы, а не команда владельца системы. Разделяй доверенные инструкции, данные сайта и доступные инструменты. Не подключай аккаунты с широкими правами для простого извлечения публичной информации.
Практика. Реши одну задачу двумя способами: Playwright с явными локаторами и browser agent. Сравни точность, стоимость, время, число ошибочных действий и воспроизводимость. Добавь схему результата и проверку evidence.
Критерий: ты понимаешь, когда агент экономит разработку, а когда обычный код надёжнее и дешевле.

66. Распределённый сбор: Celery, Redis, очереди и worker-процессы

Распределённый сбор нужен не потому, что «больше процессов всегда быстрее», а когда есть независимые задачи, долгий runtime, требования к очередям, повторным попыткам и отдельным worker-процессам. Celery — распределённая очередь задач; Redis может выступать broker/result backend. Для многих задач достаточно одного процесса asyncio или Scrapy: добавляй распределённость только после измерения узкого места.

66.1. Передавай в очередь идентификатор работы, а не гигабайты HTML

Задача worker должна быть идемпотентной: повторное выполнение не создаёт дубликаты и не портит результат. Храни полезные данные в файлах/object storage/БД, а в очереди передавай source id, URL из разрешённого scope и параметры обработки. Ошибки дели на retryable и permanent. Для постоянных ошибок используй dead-letter/manual review механизм.

# tasks.py — пример Celery 5.x + Redis

66.2. Координация и контроль нагрузки

  • Лимитируй частоту по hostname, а не только глобально.
  • Учитывай 429 и Retry-After; не запускай синхронный retry storm.
  • Используй уникальные task keys и идемпотентный UPSERT.
  • Планируй visibility timeout, acknowledgement, worker crash и повтор после потери результата.
  • Разделяй очередь обнаружения URL, извлечения, обработки файлов и нормализации.
  • Добавь лимиты размера ответа, времени, глубины обхода и числа URL на домен.
Важное различие. Очередь задач не является хранилищем данных и не гарантирует exactly-once выполнение. Практически проектируй at-least-once delivery + идемпотентную обработку. Не ставь десятки worker на один домен, если это увеличивает нагрузку или нарушает условия использования.
Практика. Раздели локальный crawler на producer и worker. Сымитируй падение worker после скачивания, но до записи; запусти задачу повторно и докажи, что в БД одна корректная запись. Добавь отдельный отчёт о permanent failures.
Критерий: ты умеешь масштабировать работу горизонтально без потери контроля над дубликатами, нагрузкой и повторными попытками.

67. Оркестрация ETL: Prefect, Apache Airflow и Dagster

Оркестратор управляет зависимостями между этапами, расписанием, параметрами запуска, повторным выполнением и наблюдаемостью. Он не заменяет HTTP-клиент, crawler или очередь задач. Выбирай его по устройству процесса:

ИнструментОсновная модельКогда рассматривать
PrefectPython flows/tasks, deployments, work poolsPython-first ETL и сравнительно гибкая оркестрация
Apache AirflowDAGs, operators, sensors, executorsПлановые batch pipelines, много зависимостей и интеграций
DagsterAssets, jobs, sensors, schedules, partitionsData platform, lineage и явное управление производными данными

67.1. Оркестрация не равна исполнителю

В DAG можно вызвать Scrapy job, HTTP batch, SQL transformation и quality check. Тяжёлые browser tasks запускай в подходящем worker/container. Оркестратор хранит состояние процесса и запускает нужный этап; сами результаты должны лежать в надёжном хранилище, а не в памяти scheduler.

# Prefect 3.x: простой Python flow (сверь deployment API своей версии)
from prefect import flow, task

@task(retries=2, retry_delay_seconds=30)
def discover_sources() -> list[str]:
    return ["source-a", "source-b"]

@task
def collect_one(source_id: str) -> dict:
    # В реальном проекте вызвать адаптер, проверить результат и сохранить.
    return {"source_id": source_id, "records": 0}

@task
def validate_batch(results: list[dict]) -> None:
    if not results:
        raise ValueError("No source results")

@flow(name="daily-public-data-collection")
def daily_collection():
    sources = discover_sources()
    results = [collect_one(source) for source in sources]
    validate_batch(results)

if __name__ == "__main__":
    daily_collection()

67.2. Обязательно добавь

  • Параметры запуска и переменные окружения без секретов в исходном коде.
  • Раздельные retry для сетевого, парсерного и data-quality этапа.
  • Backfill за исторический интервал и повтор одного partition.
  • Data quality gate: остановить публикацию, если полнота резко упала.
  • Уведомления о сбое, длительности, объёме и количестве ошибок.
  • Версионирование схемы и миграции результата.
Не усложняй заранее. Для одного запуска по расписанию может быть достаточно Task Scheduler/cron. Airflow, Prefect или Dagster оправданы, когда реально нужны граф зависимостей, retries, state, backfill, управление ресурсами и наблюдаемость.
Практика. Построй ETL из трёх этапов: загрузка → нормализация → проверка качества. Запусти его по расписанию и затем повторно выполни только провалившийся диапазон данных.
Критерий: ты можешь выбрать между cron, Prefect, Airflow и Dagster, объяснив требования, а не популярность инструмента.

68.2. Поиск в индексе Common Crawl

Сначала выбери опубликованный индекс из каталога Common Crawl, затем запроси URL-index. Индексный ответ указывает на WARC-файл и диапазон байтов; для отдельных записей можно запросить конкретный диапазон, а не скачивать весь архив. Уважай лимиты сервиса и для массовой работы используй bulk/columnar index рекомендации владельца.

import requests

# Подставь реальный индекс из списка доступных коллекций Common Crawl.
index_id = "CC-MAIN-YYYY-NN"
endpoint = f"https://index.commoncrawl.org/{index_id}-index"
params = {
    "url": "example.org/*",
    "output": "json",
    "filter": "status:200",
}
response = requests.get(endpoint, params=params, timeout=30)
response.raise_for_status()

for line in response.text.splitlines():
    if not line.strip():
        continue
    record = __import__("json").loads(line)
    print(record.get("url"), record.get("timestamp"),
          record.get("filename"), record.get("offset"), record.get("length"))

68.2.1. Скачать один WARC record по диапазону

Поля filename, offset и length позволяют запросить конкретный byte range. Всегда ограничивай размер, проверяй HTTP 206 и Content-Range. Для чтения WARC используй библиотеку warcio, а не пытайся декодировать gzip/record вручную.

from io import BytesIO
import requests
from warcio.archiveiterator import ArchiveIterator

# record — объект JSON из ответа Common Crawl Index.
max_record_size = 20 * 1024 * 1024
length = int(record["length"])
offset = int(record["offset"])
if length <= 0 or length > max_record_size:
    raise ValueError("WARC record size outside configured limit")

warc_url = "https://data.commoncrawl.org/" + record["filename"]
headers = {"Range": f"bytes={offset}-{offset + length - 1}"}
response = requests.get(warc_url, headers=headers, timeout=60)
if response.status_code != 206:
    raise RuntimeError(f"Expected 206 Partial Content, got {response.status_code}")
if len(response.content) != length:
    raise ValueError("Downloaded range length does not match index")

for warc_record in ArchiveIterator(BytesIO(response.content)):
    if warc_record.rec_type == "response":
        payload = warc_record.content_stream().read()
        print(warc_record.rec_headers.get_header("WARC-Target-URI"))
        print("payload bytes:", len(payload))
        break

68.3. Wayback и исторические данные

CDX index позволяет искать сохранённые captures по URL-шаблону, времени и mime/status-фильтрам. Используй его, чтобы ответить на вопросы об истории страницы, изменении публичных описаний и доступности URL. Не путай timestamp capture с датой события на самой странице. Проверяй конечный URL, статус и содержимое снимка.

68.4. Метаданные происхождения и лицензия

Для каждой записи сохраняй source URL, исходный identifier, время извлечения UTC, время обновления источника (если есть), архивный timestamp, имя коллекции/индекса, лицензию, attribution и метод получения. Архивная копия не отменяет авторские права, условия повторного использования, персональные данные и ограничения на распространение.

Проверка перед массовым сбором. Не сканируй бесконечно индексный endpoint и не скачивай целые WARC-файлы без необходимости. Используй диапазоны, лимиты и официальные инструкции по bulk access. Не пытайся извлекать удалённые закрытые или приватные данные из архивов.
Практика. Найди один публичный домен в Common Crawl и Wayback. Сравни две архивные даты, сохрани метаданные происхождения и объясни, почему результат нельзя автоматически считать текущим состоянием сайта.
Критерий: ты умеешь находить не только страницы, но и каталоги/архивы данных, а также сохранять происхождение и временную точность результата.
